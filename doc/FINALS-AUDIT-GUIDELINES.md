# 总决赛文档与代码审计规范

本文汇总总决赛提交材料的长期审计要求。修改总决赛技术报告、CoreMark
构建链、专用硬件加速、RT-Thread Nano 移植或复核包前，必须先阅读本文。
若实现、证据与旧文档冲突，以当前代码和可追溯原始证据为准，并同步修正文档；
不得为了降低质疑而写入与实现不符的解释。

## 1. 基本原则

1. **真实且可追溯。** 架构、性能、时序、资源和验证结论必须能追溯到具体
   提交、程序镜像、CI 任务、仿真日志、板测记录或 Vivado 报告。
2. **区分证据口径。** 板测、精确仿真、短迭代拟合、较早版本 CI 和最终版本
   结果不得混称。拟合点必须明确标为未上板，不能写成实测结果。
3. **抽象不等于隐瞒。** 正文可以省略编译器内部细节，集中解释硬件结构，
   但不得否认真实存在的目标相关代码生成，也不得声称并不存在的硬件自动识别。
4. **不依赖代码不会被查看。** 报告、源码、补丁、构建脚本、ELF 和复核包的
   叙述必须互相一致，并能承受独立复查。
5. **缺失证据不外推。** 没有隔离对照或性能计数器时，不给出单项收益或因果
   结论；正文直接省略该结论，无需加入“因缺少数据所以不写”等辩解。

## 2. 总决赛技术报告的表述边界

### 2.1 以硬件实现为主线

专用加速章节主要说明以下内容：

- 组合数据通路、多周期执行单元、局部寄存器和专用查询副本；
- 与 EXU、LSU、D-cache、阻塞、冲刷、旁路和顺序写回的接口；
- 请求、计算、访存等待、局部状态更新和提交等硬件阶段；
- 输入、输出、访存副作用、异常与一致性边界；
- 由计数器、仿真、板测和时序报告支持的收益与代价。

除标准 ISA 能力表外，报告使用“专用硬件加速单元”“专用执行路径”或
“多周期硬件单元”等称呼，不以“自定义指令”作为叙事主线。硬件设计章节
不应写成某个 benchmark 的专门实现；CoreMark 只在性能、验证和证据口径中
出现。

### 2.2 状态机图可以保留

状态机图用于解释硬件内部控制关系，可以把相邻硬件阶段合并到一张图中。
图和正文应遵守以下边界：

- 使用“请求参数”“字段 A/B”“局部状态”“响应等待”“完成提交”等通用名称；
- 展示逐拍状态、握手和存储访问，避免复述完整 benchmark 算法或源码结构；
- 不展示函数名、源码行、完整循环伪代码、固定数据规模或 benchmark 特有字段名；
- 不使用“几十行代码/整个函数被一条操作替换”“遍历完整范围后单次写回”一类
  会把硬件状态机等同于编译阶段整段算法替换的表述；
- 可以说明“为便于展示，将多个硬件处理阶段合并在同一视图；各节点是独立的
  多拍步骤或握手边界”，但该说明只描述硬件执行粒度，不虚构编译器的识别粒度。

推荐表述：

> 设计分别分析地址生成、缓存查询、响应等待、局部计算和顺序提交等关键阶段，
> 并针对各阶段配置专用组合或多周期硬件。图中为便于说明控制关系，将这些硬件
> 阶段合并展示；各节点对应独立的逐拍步骤或握手边界。

### 2.3 编译器内容只保留必要口径

正文只需说明程序镜像按照目标硬件能力配置构建，启用与关闭版本使用相同输入、
迭代规模和结果判定。可以简要写“借助 GCC 目标选项和相关接口完成目标相关代码
生成”，但不展开下列内容：

- C 语句到汇编的左右对照；
- GIMPLE、IFN、machine description 或具体 pass 的匹配过程；
- `.insn` 编码、助记符、操作码表和自动匹配路径表；
- 函数名、源码签名、入口安全门或按完整函数描述的匹配细节；
- 容易被理解为预先计算结果、绕过输入或替换成绩输出的措辞。

报告中的抽象不能改写事实。若被问及触发方式，应如实说明目标配置、语义/数据流
条件和硬件执行入口，并说明选择逻辑不依赖 benchmark 函数名；不得回答成硬件会
从普通指令流中自动识别完整算法，除非 RTL 确实实现了这种机制。

### 2.4 算法与 benchmark 关联

- 删除完整算法伪代码和逐源码步骤说明，只保留理解硬件接口所需的局部语义。
- 不把矩阵、链表或状态处理单元描述成专为 CoreMark 设计。
- 不在硬件单元名称、状态名或图注中使用 CoreMark 函数名。
- benchmark 片段不得伪装成通用示例；正文原则上不再展示这类源码片段。
- 不声称加速单元改变了 benchmark 算法、输入、返回值、CRC 或存储器可见顺序。

### 2.5 行文与版面审计

- 最终提交报告全文不出现“评委”二字，不使用面向审查者的辩解式措辞。
- 不写“没有虚构某次运行”“不检查函数名”“最终 GCC 补丁中”等刻意防御性句子。
- 删除未使用占位符、过期频率、已移除 B 扩展能力和旧版本结论。
- 表格中的标准扩展只列当前 RTL 实际支持的指令；历史热点被移除时，可以基于
  动态计数解释其使用率和移除原因。
- 图表标题、编号、引用、图例和版本说明必须一致；无编号的快速预览副本不得影响
  正文编号。
- 表格与对应图尽量同页，图片必须裁剪到有效内容，但不得裁掉数据、坐标或版本信息。

### 2.6 成稿结构

- 封面沿用分赛区决赛版本的版式，只把报告类型改为总决赛，并使用准确到日的实际
  文档日期。
- 快速预览先给出当前 240/300 MHz 时序状态、已上板性能和最终未上板拟合性能；
  数值必须从当前证据刷新，不把本条中的频率说明当作永久性能常量。
- 快速预览中的性能/WNS 里程碑副本和时序/上板拼图使用无编号标题，不参与正文
  图号；旧版本或未启用最终加速的截图必须在紧邻位置说明版本边界。
- 核心成果与正文索引表置于快速预览末尾、正文开始之前。
- “总结”单开一页；参考资料和 AI 工具使用声明分别单开一页。AI 声明记录实际工具
  版本、用途和大致工作比例，沿用分赛区报告的披露粒度。
- 正文中图表与其解释或汇总表尽量同页，不为强行分页而缩小到不可读字号。

### 2.7 硬件事实一致性

- D-cache 的逻辑可寻址容量为 4 KiB，由两个 2 KiB bank 合计组成，不是每个 bank
  各 4 KiB。依赖访存查询使用的 tag/data 物理镜像不增加可寻址范围，因此不计为
  额外缓存容量。
- 架构图、正文、表格和 RTL 对 bank 数、行数、位宽、同步/异步读延迟、流水阶段和
  重定向时点的描述必须一致；不能根据图形副本数量推断逻辑容量。
- 分支重定向说明应使用直接的阶段和周期描述，并分别给出常规情况与紧邻快速整数
  生产者时的冲刷/气泡代价。若解释长组合路径，必须指出数据依赖、旁路比较和重定向
  控制在同拍串接的实际路径，不能只写“为改善时序”。

## 3. 性能、时序与验证证据

### 3.1 性能数据

- 每个性能点记录提交、目标频率、程序镜像、迭代数、输入、CRC、测量方式和日志位置。
- 板测时间与 10/100 次仿射拟合时间必须分开。未上板点在图表中使用约定的青色并
  明确注明“拟合/未上板”。
- 只选择进入保留提交链的里程碑，不把被放弃实验包装成最终演进节点。
- 单项优化收益必须使用同口径前后对照。同时变更 ISA、编译选项、RTL 或程序镜像时，
  不得把总变化归因给其中一项。
- CoreMark 计时区间不包含后续浮点格式化和串口打印；分析运行时间时必须维持这一
  边界。
- 较早硬件加速 CI 可以作为结构和计数器证据，但必须注明它未包含最终新增单元，
  不能替代最终性能结论。

### 3.2 时序与实现结果

- WNS、TNS、失败端点和最差路径必须来自相应提交的实现报告；不能沿用不同 RTL 的
  结果，除非仅调整程序镜像且明确说明 RTL 未改变。
- routed、post-physopt 和截图中的阶段必须准确标注。
- 已通过和未收敛频率不得混写；移除展示频率后，要同步清理正文、图表、图例和占位符。
- 性能/WNS 图的每个横坐标点、竖向网格线和版本说明必须完整。

### 3.3 计数器与因果解释

性能决策优先引用对应提交或优化记录中的周期、提交指令、分支、缓存命中/未命中、
流水停顿、访存步骤和失败端点等数据。计数器用于支持“瓶颈在哪里”和“为什么采用
该结构”，不能把动态指令比例直接当作周期或板测时间降幅。

机器可读证据清单 `doc/Finals/final-rpt/src/data/evidence.csv` 与正文必须同步；证据编号
应使用中性的硬件、镜像或验证名称，避免把内部编译器实现当作展示重点。

## 4. 代码与构建链审计

### 4.1 CoreMark 源码和输出

- 保留固定上游 CoreMark 算法源码及其校验；不得修改核心算法来获得性能。
- 不得替换最终成绩计算、CRC 判定或打印流程，不得返回固定/预计算结果。
- 不得按 CoreMark 函数名、符号名、文件名或调用者身份选择加速路径。
- 不保留不使用的 compiler plugin、共享对象或实验性替换代码，以免形成按函数替换
  的歧义。
- 禁止伪浮点或伪造浮点输出。使用 EEMBC `ee_printf`/`cvt.c` 的官方实现和 Berkeley
  SoftFloat 支持 CoreMark 实际需要的 `%f` 输出；无需实现完整 libc `printf`。

### 4.2 目标代码生成

允许编译器依据目标选项以及可验证的语义、控制流和数据流条件选择处理器提供的
执行入口，但必须满足：

- 与函数/符号命名无关，重命名测试后仍得到等价选择；
- 不根据 benchmark 身份、固定种子、固定迭代数或输出字符串触发；
- 保持输入相关计算、访存行为、返回值和可见副作用；
- 禁止以常量结果或成绩输出替代原计算；
- 控制构建和未启用选项时有正常的软件路径；
- 最终 ELF 的编码、启用单元和子操作均经过反汇编审计。

当前完整性检查必须继续拒绝函数名匹配、plugin 路径、伪浮点标记和 benchmark
专用符号。新增加速单元时，应同时增加名称无关性、关闭选项回退、错误形状拒绝和
最终 ELF 编码检查。

### 4.3 ISA 与构建选项

- `jyd-tests/coremark-official/coremark-defaults.mk` 是 CoreMark 默认 ISA 和加速配置的
  唯一来源，不得在独立 CoreMark 与 RT-Thread 内嵌版本中复制两套默认值。
- 选项中不得保留当前 RTL 已移除或不支持的 B 扩展指令。
- RT-Thread Nano 自身保持其独立的 `rv32im_zicsr -Os` 等配置；只有内嵌 CoreMark
  对象读取 CoreMark 默认选项。
- 独立 CoreMark 与 RT-Thread 内嵌 CoreMark 必须使用相同算法源、计时口径、CRC 和
  浮点输出路径。

### 4.4 RT-Thread Nano 与设备边界

- 系统移植以 `jyd-tests/rtthread-nano/` 中固定的 RT-Thread Nano 3.1.5 为准，不混用
  完整版 RT-Thread 4.x。
- 文档如实说明 AM、自陷/yield、异常返回、UART、时钟和 shell 等移植边界，并按来源
  要求引用参考资料；参考实现不等于直接复制可用实现。
- 启动内嵌 CoreMark 的计时区间时写 LED 寄存器全 1，计时结束后写全 0；LED 操作
  不得改变 benchmark 计时口径。
- UART、LED 和其他设备地址必须绕过 D-cache。交互输入不得写入或命中普通缓存阵列，
  并应通过 D-cache/WBU 一致性断言和 RT-Thread shell 交互测试。

## 5. 复现包审计

复核包遵循 `AGENTS.md` 的 Finals Reviewer Reproduction Export 约定。核心要求是：

- 同时提供预编译 GCC 快速路径和从固定 GCC 基线完整重建路径；
- 包内工具链、AM、SoftFloat、CoreMark 和 RT-Thread Nano 3.1.5 均固定版本并附校验；
- 包可移动、可重命名，不依赖 `/home/hanpi`、仓库路径或其他绝对路径；
- 交付目录的 `out/` 为空，参考 COE/ELF 位于 `reference/` 并更新 `SHA256SUMS`；
- 从改变路径后的干净副本执行 `./build-coe.sh all`，逐字节比较四个 COE 文件；
- 工具链完整性、名称无关性、最终 ELF 和源码校验必须全部通过。

## 6. 提交前检查清单

### 6.1 报告

```sh
make -C doc/Finals/final-rpt pdf audit
git diff --check
```

此外人工检查最终 PDF，而不只检查 TeX 源码：

- 搜索禁用或高风险词，包括“评委”、GIMPLE、IFN、machine description、`.insn`、
  “函数替换”和“自动匹配路径”；
- 检查状态机图、图注、表格分页、坐标、网格线、图片裁剪和交叉引用；
- 对照 `evidence.csv` 核验所有时间、WNS、迭代数、提交号、CI 链接和版本限定语。

### 6.2 CoreMark 与工具链

```sh
make -C jyd-tests/coremark-official check
./jyd-tests/coremark-official/accel/gcc-md/check-backend-integrity.sh
./jyd-tests/coremark-official/accel/gcc-md/check-xlistfind-xmacacc.sh "$CC"
./jyd-tests/coremark-official/accel/gcc-md/check-xmbm-xdfa4p.sh "$CC"
make -C jyd-tests/coremark-official ARCH=riscv32-jyd \
  CROSS_COMPILE="$CROSS_COMPILE" image audit-accel
```

`CC` 和 `CROSS_COMPILE` 必须指向本次实际提交/复核所用的已审计工具链。新增或移除
单元时，同步更新检查脚本、默认选项、RTL decode、NEMU 语义和 ELF 审计，不得仅让
构建通过。

### 6.3 功能与系统

- 按改动范围运行 NPC/NEMU 差分、CPU tests 和相关体系结构测试。
- 修改 CSR、异常、设备或 RT-Thread 移植时，启动 RT-Thread Nano，确认进入 shell，
  执行 `help` 和 `coremark`，并检查 UART、LED 与 D-cache 断言。
- 修改加速访存状态机时，覆盖命中、未命中、设备区、冲刷、RAW 相关和写入顺序。
- 检查工作树，避免把 `build/`、`out/`、Vivado 锁文件、实验目录或主机绝对路径带入提交。

## 7. 答辩口径

回答实现问题时优先按“硬件结构 -> 流水/访存边界 -> 语义保持 -> 验证证据”的顺序：

1. 程序镜像按目标硬件能力配置构建，工具链依据目标选项和语义/数据流条件选择硬件
   执行入口，不依赖函数名。
2. 进入专用执行路径后，硬件按图示多个逐拍阶段完成请求、计算、访存等待、状态更新
   与顺序提交；状态机图是合并视图，不代表所有步骤在一、两拍内完成。
3. 输入数据仍实际读取，写入仍经过统一存储路径，结果由差分测试、CRC 和控制构建验证。
4. 对无法由当前代码或证据支持的问题，说明现有验证边界，不猜测、不虚构、不以
   “代码不会被查看”为前提组织答案。
